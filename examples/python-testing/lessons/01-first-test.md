# 第一课：写出一个能解释的单元测试

**能力：c-test。前置：会定义函数、导入模块、运行 Python。**

规划用时约 1 小时，其中阅读 15 分钟、动手 30 分钟、验收 15 分钟；这不是规定每个人必须以同样速度完成。

## 从哪里学

阅读 [Basic example](https://docs.python.org/3/library/unittest.html#basic-example) 和 [Test Discovery](https://docs.python.org/3/library/unittest.html#test-discovery)。这两段分别支持最小测试的写法和运行入口。来源记录见 [课程证据表](../resources.json)。

## 为什么不是打印结果就够了？

考虑 `normalize_scores([30, 60])`：它按本实验契约应返回 `[0.3, 0.6]`。打印后靠肉眼比较，需要每次重复判断；写成测试则把预期保留下来。测试不是“再算一遍同样的代码”，而是把**外部可观察的约定**写清楚。

把测试分为三段理解：准备输入，调用目标函数，检查结果。预期值尽量由独立的简单推导得到，不要复制待测函数的内部算法来算预期，否则实现与测试可能一起犯错。

## 一个与主练习不同的小例子

假设我们约定 `double(x)` 返回 `x * 2`，可以这样检验：

```python
import unittest


def double(x):
    return x * 2


class TestDouble(unittest.TestCase):
    def test_positive(self):
        observed = double(4)
        self.assertEqual(observed, 8)
```

这段例子里，`4` 是输入，`8` 是根据契约得到的预期，断言比较的是观察结果与预期。该例子只说明一个正常情况，并没有证明所有输入都正确。把预期暂时改成 `9`，应当看到失败；恢复后才应通过。

## 轮到你

进入你个人课程副本的 `lab/`，阅读 `normalize_scores.py` 的函数文档，暂时不要看参考测试。新建 `test_mine.py`，独立覆盖：普通整数分数、0 与 100 两端、单个合法浮点分数。对浮点结果决定使用什么断言，并解释原因。

```bash
python -m unittest -v test_mine
```

故意把自己某一个正确预期改错，记录失败的断言和差异，然后恢复。这个动作是在验证“测试真的能报警”，不是为了交一个永远失败的测试集。

## 提示

先用固定的小输入明确预期；浮点值比较可以查官方断言方法，不需要先学完整个测试框架。测试名字应说明正在验证什么。

## 产物与通过标准

提交 `test_mine.py` 和三句话：哪个输入对应哪个预期、一次故意失败的原因、为何测试通过不等于证明所有情况正确。至少三条自己编写的测试正常通过，并能解释失败实验，才进入第二课。只运行附带的参考测试不算独立完成。

若测试根本没有被发现，先检查文件位置、模块导入和测试命名，不要急着怀疑业务函数。若预期错了，先回到输入契约。
